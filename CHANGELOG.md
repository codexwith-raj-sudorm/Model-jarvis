## Session 1 — Concept
Started as "Sahayak": a 100% offline assistant concept doc (architecture, model tiers, speech stack, memory/RAG, roadmap, license audit). Research snapshot: Qwen3-1.7B best small all-rounder (Apache-2.0), Gemma-3-1B for 4–6 GB phones, Phi-4-mini/Qwen3-4B for flagships.

## Session 2 — Capabilities walkthrough
Mapped exactly what the system can and cannot do (honest limits: no live internet knowledge, not frontier-model quality, device-dependent speed).

## Session 3 — Rename + internet
Renamed to **JARVIS**; redesigned as *local-first hybrid*: opt-in web layer added to the design doc (free sources table, privacy design, "when to go online" router problem).

## Session 4 — Phase 0 build
Full Android scaffold (46 files): Gradle version catalog, manifest, arc-reactor icon, **llama.cpp JNI bridge written against the live `llama.h` API** (fetched and verified that day: `llama_model_load_from_file`, `llama_init_from_model`, `llama_batch_get_one`, sampler chain, `llama_vocab_is_eog`), UTF-8-safe token streaming (byte-level BPE partial-rune buffering), chat templates for 4 model families, agent orchestrator with TOOL_CALL loop, 8 tools, WebFetcher + Readability, SQLite memory, Compose chat UI, model scripts.

## Session 5 — System integration
JARVIS became a real system assistant: `VoiceInteractionService` (+ session service, manifest pattern verified against AOSP docs), translucent voice-first overlay with auto-mic, Quick Settings tile, shared `ChatLog` + warm-engine reuse across screens.

## Session 6 — Voice-first refocus
User: *"main focus should be on connecting to the internet and answering via voice."* Mini-RAG web search (BM25 paragraph ranking — small models can't read whole pages), `news` tool (Google News RSS), `WebIntents` fresh-data router (English + Hindi/Hinglish), voice-optimized answering (short, no markdown, source attribution), `SpeechFormatter`, **hands-free loop** (TTS onDone → mic re-opens), barge-in on tap, web ON by default (persisted). *Engineering note: discovered that parallel edits to the same file had silently clobbered each other in earlier batches; re-verified everything with grep sweeps and re-applied lost edits — all subsequent same-file edits were made strictly sequential.*

## Session 7 — Fully-offline voice (sherpa-onnx)
Verified the real Kotlin API file-by-file from upstream (`OnlineRecognizer.kt`, `OnlineStream.kt`, `Tts.kt`, `FeatureConfig.kt`) and the artifact coordinates from sherpa's own `jitpack.yml` (`com.k2fsa.sherpa.onnx:sherpa-onnx:1.12.40` via JitPack). Built `VoiceInput`/`SpeechOutput` abstractions; `SherpaSttEngine` (AudioRecord 16 kHz → streaming zipformer, endpoint-detected turn taking, live partials) and `SherpaTtsEngine` (Piper/VITS, chunk-streamed via `generateWithCallback` into AudioTrack, abortable = instant barge-in). Auto-selection in `ServiceLocator` with system-engine fallback; `get_voice_models.sh`.

## Session 8 — Wake word
Discovered sherpa's bilingual **KWS zipformer (3M params, int8 encoder ≈ 4.4 MB)** with phoneme-based custom keywords → **"Hey JARVIS" needs zero training**: `JARVIS @JH @AA1 @R @V @AH0 @S` (CMU phonemes, auto-installed). Dual driver (KWS preferred, ASR-phrase fallback), `JarvisWakeService` microphone foreground service (persistent notification, mic handoff to overlay, pause/resume), 👂 UI toggle with POST_NOTIFICATIONS handling on 13+.

## Session 11 — Concurrency hardening
Two crash-class bugs fixed: (1) *JNI thread safety* — the llama.cpp bridge used unlocked global state, so tapping stop or switching models mid-generation could segfault; every entry point is now serialized behind a `std::mutex`, plus a cooperative `std::atomic` abort flag with a new `nativeStopGenerate()` (stop is instant and callable from the UI thread; load/unload set abort *before* locking so they never wait long; `nativeIsLoaded` reads a lock-free atomic so status checks never block behind a generation). Bonus: a full re-read of `llama_jni.cpp` revealed the `std::string pending` declaration had been lost to the earlier edit race (undeclared identifier — wouldn't have compiled); restored in the rewrite. (2) *Main-thread unblocking* — `SherpaSttEngine.stop()`/`SherpaTtsEngine.stop()` joined their worker threads on the caller (UI) thread for up to ~2 s → stutter/ANR; joins stripped: cleanup now happens on the workers' own threads (`finally` blocks), TTS engine release moved to a daemon thread, the STT mic-open got a 3×200 ms handoff-grace retry, and the wake service's `onDestroy` join was removed for the same reason. `ChatViewModel.stopGeneration()` now calls `engine.stopGenerate()` so the ■ button actually halts the native token loop instead of just cancelling the coroutine.

## Session 12 — Context overflow & UTF-8 hardening
(1) *Mini-RAG text truncation* — web tool results could reach several KB; stacked into history they overflowed the model context and `llama_tokenize` returned a negative count (graceful error, but a dead turn). Three-layer fix: a strict **1500-character clamp on every tool result** at the single point where results enter history (`Orchestrator.MAX_TOOL_RESULT_CHARS` — guards all current and future tools), a **whole-prompt character budget** (8000 chars; history is trimmed oldest-first, always preserving the last 2 turns; sized for Hindi/Hinglish which tokenize at ~2 chars/token on Qwen), and WebSearchTool portioning tuned (top 4 passages × 350 chars) so a normal result lands *under* the clamp instead of being mid-sentence truncated. (2) *UTF-8 stream safety* — the partial-rune buffer (hold bytes until the character completes) already existed from Phase 0; the real remaining gap was malformed input: a stray invalid byte (bad lead, orphaned continuation run, overlong C0/C1, F5+) would still reach `NewStringUTF` and abort the JVM, and the full-result return path had no validation at all. Added `sanitize_utf8()` (drops invalid bytes, stops at partial tails) — now *both* the streaming flush (refactored into one `flush_pending` lambda) and the final return pass through it.
